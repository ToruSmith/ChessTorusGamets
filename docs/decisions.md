# 決策紀錄

重要的技術與流程決定，以及當時的理由。新的寫在最上面。改變既有決定時，新增一筆並註明取代哪一筆。

## M3：線上對戰

### D22. 不做在線狀態與房間清理

第一版不顯示對手是否在線（presence），也不自動刪除舊房間。房間資料很小，需要時可以在 Firebase Console 手動清理，
或之後加上排程（不能自建伺服器，所以要另外評估）。

### D21. 觀戰者只能看，而且同樣不能用引擎

第三位以後進入房間的人是觀戰者。`analysisAllowed` 對觀戰者一樣只有對局結束後才開放，避免轉述引擎建議給玩家。

### D20. 從大廳按「加入」就直接入座

大廳的按鈕先入座再進房間；用房號或連結進來的人則在房間裡看到「加入對局」按鈕，也可以只觀戰。

### D19. 再戰由上一盤的白方建立

雙方都按「再來一局」後，由上一盤的白方建立新房間並寫入 `next`。只由一方建立，就不會同時出現兩個房間；
規則也只允許 `next` 寫一次，而且必須和新房間同一次寫入，所以即使重複嘗試也不會留下垃圾資料。

### D18. e2e 用同一瀏覽器的本機後端

e2e 版用 `localStorage` 加 `storage` 事件模擬伺服器，兩個分頁就能對局，不需要真的 Firebase 或模擬器。
一開始用 BroadcastChannel 通知，但訊息會比 `localStorage` 的跨分頁同步早到，導致分頁讀到舊資料（再戰測試 10 次失敗 9 次）；
改用 `storage` 事件後，重複 80 次全部通過。

### D17. 規則用自製的模擬器測試

Firebase 官方模擬器需要 Java 與 firebase-tools，CI 很重。`tests/helpers/rules-db.ts` 依文件語意求值同一份
`database.rules.json`，讓每次寫入都經過規則。為了讓兩種解讀都成立，規則不依賴「上層 `.validate` 是否會在子節點寫入時執行」。
官方引擎與模擬器若有差異，以官方為準，修改規則後應在 Rules Playground 再確認。

### D16. 依賴版本

- `firebase` 固定 13.1.0（13.2.0 發布不到兩週）。
- `@grpc/grpc-js` 用 `overrides` 固定在 1.13.7，修掉 `npm audit` 的高風險警告。
  它只被 Firestore 在 Node 環境使用，本專案沒有用到，也不會打包進網站；用 overrides 是為了讓 audit 保持乾淨。

### D15. `RoomBackend` 是低階介面

介面只有讀、監看、多路徑更新、伺服器時間與大廳查詢，房間的業務邏輯都寫在 `online/session.ts`。
**理由**：Firebase、e2e 本機後端、規則模擬器三種實作都很薄，業務邏輯只有一份，而且每次寫入都能在測試中經過規則。

## M2：雙人同機

### D14. 棋盤暫時只支援指標操作

點選與拖曳都用 Pointer Events，滑鼠、觸控、觸控筆都能用。鍵盤操作棋盤（方向鍵移動游標、Enter 選取）
留到之後再做，目前用按鈕操作的功能（悔棋、提和、認輸等）都可以用鍵盤。
**理由**：先完成主要互動；鍵盤操作需要另外設計焦點與螢幕閱讀器的朗讀方式。

### D13. 雙人同機的對局存在 `localStorage`

畫面層把 `LocalMatch.toJSON()` 存在 `chess.local.v1`，重新整理後接著下；讀不到或格式不對就當作沒有存檔。
計時對局在關閉分頁時棋鐘仍照真實時間計算，回來時可能已經超時。
**理由**：結果完全由紀錄重演，存紀錄就夠了；不另外做「暫停」以免和線上規則不一致。

### D12. 提和、認輸、聲明和棋由輪到的一方提出

同一台裝置上分不出是誰按的，所以這些動作都算輪到走棋的一方；接受和棋則由提和方的對手按。
拒絕提和不需要按鈕，對手直接走棋就失效（D6）。

### D11. 計時對局不能悔棋；棋鐘從第一手開始

悔棋會讓時間戳與棋步對不上，所以只有不計時的對局能悔棋。悔棋時，最後一手之後的事件（例如認輸）也一起移除。
棋鐘在白方走第一手時才開始，第一手不耗時，避免開局前就扣時間。

### D10. `state/` 用自製的小型 store，不引入狀態管理套件

`WritableStore` 加上 `useSyncExternalStore` 就夠用，而且 `state/` 可以不依賴 React，在 Node 測試裡直接跑。

## M1：規則核心

### D9. 只接受完全相符的合法手

`Game.play` 先在合法手清單裡找出 from、to、升變棋子都相同的那一步才走，不把輸入直接交給 chess.js。
**理由**：chess.js 對缺少或多餘的升變字母有容錯；線上棋步要能明確判為不合法（重演判負），不能被默默修正。

### D8. 局面鍵使用 chess.js 的 FEN 前四欄

重複局面的判定以「棋子位置、輪到誰、王車易位權、過路兵格」為鍵。chess.js 1.4 只在**真的能合法吃過路兵**時
才把過路兵格寫進 FEN，正好符合 FIDE 9.2.2。王車易位權在載入 FEN 時就檢查必須與王、車位置相符，
所以 FEN 裡的易位權等於實際的易位權。這兩點都有測試。

### D7. 死局面與 6.9 例外採保守判斷

只偵測子力不足：王對王、王加一枚輕子對王、所有主教都在同色格。兵互鎖等其他死局面不偵測，
對局會由 75 回合或五次重複結束。超時時，只有對手沒有王以外的棋子、或盤面已是子力不足的死局面時才判和。
**理由**：誤判「不可能將死」會把應該贏的人判成和棋；保守的一方最多是少判和，而且之後容易補強。

### D6. 提和與聲明和棋的細節

- 提和送出後不能撤回。**對手**走下一步時失效；提和方自己走棋不會讓它失效（9.1.2.3）。
- 雙方都提和視為同意和棋。
- 聲明和棋：輪到的一方依目前局面聲明，或在同一次寫入裡「走這步並聲明」（同 ply、同時間戳）。
- 條件不成立的聲明直接忽略，對局繼續。FIDE 9.5 對錯誤聲明給對手加時的罰則，線上不實作。

### D5. `replayMatch` 是所有模式的唯一判定

雙人同機用本機時間、線上用伺服器時間，但都把「棋步＋時間戳＋事件」交給同一個 `replayMatch`。
**理由**：同一份資料必然得到同一個結果；本機與線上不會出現規則差異，也只需要測一套。

### D4. 棋鐘：到 0 即超時

時間剛好用完（`t >= deadline`）就算超時；在期限之前送出的棋步才有效，之後加上費雪制加秒。
第一手的時間從 `startedAt`（第二位玩家入座）開始算。

## M0：專案骨架

### D3. 勝負與和棋依 FIDE 正式比賽規定

原需求是「自動判定三次重複與 50 回合」，使用者在 M0 審查時改為依正式規定：
五次重複與 75 回合自動和棋，三次重複與 50 回合需要聲明。取代原需求。

### D2. 分層規則用測試強制

`tests/helpers/import-rules.ts` 以資料定義各層可依賴的對象與外部套件限制，`npm test` 時掃描 `src/`。
**理由**：不需要另外安裝 ESLint，規則和文件可以一起維護。

### D1. 用 Node 原生的 TypeScript 執行測試

Node ≥ 22.18 可以直接執行 `.ts`，所以相對 import 一律寫副檔名，並開啟 `erasableSyntaxOnly`。
**理由**：少一個工具（tsx），測試與瀏覽器跑的是同一份原始碼。
